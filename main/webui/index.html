  Saving writes the mrb_script partition and reboots the board to apply
  it - same effect as bin/upload_mruby_script.py, but over WiFi instead
  of serial. The board is unreachable for a few seconds while it
  restarts; this page polls it and reloads itself automatically once
  it's back (give up and refresh manually if it takes longer than 30s).
  Syntax highlighting is loaded from a CDN (cdn.jsdelivr.net) - if this
  network has no internet access, editing still works as a plain textarea.




  "Sleep now" manually triggers the USB-suspend power-saving reaction
  (WiFi off) - use it if you connected to a PC that was already suspended
  before this board booted, since that never fires the automatic detection
  (only a live suspend/resume transition does). WiFi stops shortly after,
  so this page becomes unreachable until the PC actually resumes; only use
  it when the PC really is suspended, or it'll stay off until reset.




  "Unpair BLE" forgets every PC currently bonded over Bluetooth (see the
  "ble:" line above) so a different PC can pair next - pairing itself
  still happens entirely from that PC's own OS Bluetooth settings (no
  PIN/passkey, no separate step here). Harmless to click if no `:ble` sink
  is declared in the script or nothing is paired yet. The onboard LED
  double-blinks while advertising/waiting for a BLE connection (once WiFi
  itself is connected and idle - it takes priority while still connecting).




  "Start/Stop debug stream" opens a second, dedicated connection (port
  ) that live-streams the script's
  debug_print(...) calls below. It costs the board a bit of
  RAM for as long as it's running, so it's opt-in rather than always on -
  click "Stop debug stream" when done watching to free it back up. The
  button reflects the board's actual state (fetched from /api/status), not
  just what this tab remembers, so reloading or reopening this page while
  it's still running picks the log back up automatically instead of
  losing track of it. It also survives a reboot (Save/Update firmware
  both reboot the board): starting it is remembered, so it comes back on
  its own afterwards instead of needing "Start" clicked again after every
  save - only clicking "Stop" actually turns it off for good. One viewer
  at a time is the expected use.




  "Update firmware" flashes a new esp32-kvm-ip .bin (an
  idf.py build output, e.g. build.host/esp32-kvm-ip.bin
  for the Host role) over WiFi instead of needing a USB cable. It's
  written to the currently-inactive slot and only takes effect after a
  reboot. If the new firmware crashes or never gets as far as connecting
  to WiFi, the board automatically reverts to the previous firmware on
  its next boot - the "firmware:" line above shows which slot is running
  and whether it's confirmed "valid" yet. Only flash a .bin
  actually built for this board/role - there's no compatibility check.
